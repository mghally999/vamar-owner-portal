# Vamar Owner Portal: independent audit (22 Oct 2026)

Scope: the whole monorepo at commit `953010b` (branch `main`, clean tree, CI green) and the live
deployment (Worker `vamar-owner-portal`, Neon project in eu-central-1, Firebase project
`vamar-owner-portal-c55c2`, EAS preview APK). Read-only: no code was changed before this file was
committed. Every finding carries a file and line or a command and its output. Numbers were measured
on the development laptop (Windows 11, Node 24, Postgres 17.11 local cluster) unless marked "live".

## 1. Verdict

**Not yet production-grade; a sound core with an unhardened shell.** The data path is well built:
every staff write runs in one transaction with its audit row, owner isolation goes through a single
scope helper and is proven by an isolation test suite, SQL is fully parameterised, refresh tokens
rotate with replay detection, TOTP secrets are AES-GCM encrypted, security headers are strict, and
the business rules live in one tested package. Around that core the system treats failure as
somebody else's problem: outbound calls have no timeouts or retries, the push pipeline marks work
done before sending and can never retry, the cron has no error handling, the health check never
touches the database, the clients sign users out on any transient error, and two configuration
shaped faults (an environment flag that defaults to `development`, a Firebase signature bypass gated
by one env var) pass every test and would bite in production. Performance is fine for one owner and
collapses on the staff overview under office load (27 requests/s, p50 1.8 s at 50 concurrent users
on the synthetic portfolio). Maintainability is strong at the type level (zero `any`, zero
suppressions) and weak at the structure level (59 functions over 60 lines, nine files over 400
lines, rules copied into SQL and cron code).

Overall score **6.1 / 10** (scorecard in section 4). Target after Phase B to H: 8+ on every line.
